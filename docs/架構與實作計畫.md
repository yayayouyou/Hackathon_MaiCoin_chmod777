# MAIA 架構與實作計畫 v3 — 實作對齊版

> **v3 改了什麼**:v2 是在「後端還只有 2,000 行純標準庫骨架」時寫的規劃書,描述的是**打算怎麼做**。
> `max-ai-trading-agent` 併入 `agent-core/` 之後,真實系統與 v2 的規劃有三處**方向性不同**,而那三處若照 v2 寫進簡報就是不實陳述。本版以實際程式碼為準重寫。
>
> 所有數字與行號都可回程式碼查證。文件與程式碼衝突時以程式碼為準。

## 0. v2 被推翻的三件事(列出來,避免有人回頭引用)

| v2 的說法 | 實際情況 | 證據 |
|---|---|---|
| **「Strands Agents SDK on Bedrock 主線」**(v2 出現六處) | **全庫 grep `strands` 零命中。** agent loop 是手寫的 `for` 迴圈 | `agent/ollama_agent.py:469` `for current_step in range(1, max_steps + 1)`,`max_steps=8` |
| 「5 個 `dna_*` + 5 個 `max_*` 唯讀工具」 | 9 個家族、72 支 skill、對外 106+ 個 tool schema | `skills/` 74 檔 |
| 「Orchestrator + Market-Research + Portfolio-Analysis + Risk + Execution 五 agent supervisor 拓撲」 | 1 個 orchestrator + **Critic** + **Reader** 兩個真子 agent。其餘「角色」是工具家族不是 agent | `agent/critic_agent.py`、`agent/reader_agent.py` |

**這不是降級。** 真實系統在 HITL 下單互鎖、審計鏈、不可信內容淨化、四道實盤防線上,都超出 v2 的規劃深度。v2 錯的是「用了什麼框架」與「有幾個 agent」,不是能力。

## 2. Agent 架構(真實版)

### 2.1 推理迴圈

`agent/ollama_agent.py` 的 `run_agent_turn()` —— **provider-agnostic 的手寫 ReAct 迴圈**,不是任何 SDK 的 model-driven loop。

```
for current_step in 1..max_steps(8):
    ① yield status 事件(給前端「正在做什麼」)
    ② provider.chat(messages, tools=候選工具集)
    ③ 有 tool_calls → 逐一執行
         ├ 不可信來源 → reader_agent.sanitize()
         ├ 寫入型工具 → trade_approval 互鎖,yield approval_request 後暫停
         └ 結果回填 messages
    ④ 無 tool_calls → 產生最終答案
    ⑤ critic_agent.evaluate_decision() 複審
         └ 回饋不含「審查通過」→ 附加免責與 Critic 意見
```

**它是 provider-agnostic 的**:同一份迴圈跑 Bedrock / Ollama / OpenRouter,靠 `agent/llm/base.py` 的 `LLMProvider` 介面。切換供應商主迴圈零改動。

### 2.2 三段式工具檢索(這是規模問題的解法)

106+ 個工具塞不進一次 prompt。`agent/tool_router.py` 的 `select_tools()`:

1. **關鍵字意圖比對** —— 命中多個意圖取聯集
2. **embedding 語意檢索** —— 關鍵字完全沒命中時補救(`tool_embeddings.py`)
3. **信心自適應候選數** —— 分數越低給越寬的候選集(低信心 `k=14`)

實測:同一個問題會路由出 9 / 15 / 24 / 62 個工具不等。決策寫進 `routing_log.jsonl` 供事後找「漏工具」的洞。

⚠️ **已知缺口**:embedding 走本地 ollama 的 bge-m3(`tool_embeddings.py:27-31`),上雲後會**靜默**退化成純關鍵字,而且失敗一次後 `_index_failed = True` 永不重試。解法是容器內預先 bake 向量索引 json —— 既有的 sha256 簽章快取機制已支援,工具描述不變就不需要 embedding 服務,零成本。

### 2.3 兩個真子 agent

| 子 agent | 何時觸發 | 做什麼 |
|---|---|---|
| **Reader** `reader_agent.py`(274 行) | `is_untrusted(tool_name)` 為真且執行成功時 | 破解零寬字 / 同形字 / leet / 拆字 / base64 / hex 六種混淆。base64 是**解碼後**含注入關鍵字才判定,以免誤殺鏈上地址與 txid |
| **Critic** `critic_agent.py` | 產生最終答案後 | 複審決策;回饋不含「審查通過」就附加分級免責與 Critic 意見 |

Reader 攔截到注入時會 yield `reader` 事件(含 `injection_detected` / `flags`)—— 這是「AI 設計 15%」的具體展示點。

### 2.4 HITL 下單互鎖

`agent/trade_approval.py` + `skills/execution/live_guard.py`。模型**只能提議,不能執行**:

```
模型提議下單
  → SHA256 凍結計畫(只雜湊意圖欄位,排除市價以免價格跳動造成 mismatch)
  → yield approval_request { token, plan, hash, summary }
  → 120 秒單調時鐘 TTL(防 NTP 回撥)
  → 使用者核准
  → 執行前再驗一次雜湊
  → 依「凍結在計畫裡的模式」而非重讀環境變數
  → 四道防線再跑一次
```

**四道實盤防線**(`live_guard.py:62-283`):

1. **Kill switch** —— 刻意用檔案。原始碼註解:「出事當下 touch 一個檔案任何人都做得到」
2. **`LIVE_UNTIL` 授權到期**
3. **24h 滾動曝險上限** —— 20 萬 TWD / 20 筆
4. **決策台帳** —— 被擋下的決策也寫。註解:「只記成功的等於只留下一半的故事」

18 個測試覆蓋每道防線的繞過情境。

### 2.5 審計鏈

`agent/audit_logger.py:35-57` —— 開場先讀檔取上一筆 `chain_hash`,是**跨會話的一條真鏈**而非每筆獨立雜湊。宣稱「每一個 AI 決策都可回溯且可驗證未被竄改」時,這是實作依據。

## 4. Bedrock Converse API 實作要點

> 這一節從 v2 保留 —— 它描述的是 Bedrock 的機制,不受架構變更影響,而 `agent/llm/bedrock.py` 正是照這套做的。

- 工具定義放 `toolConfig.tools[].toolSpec`(`name` / `description` / `inputSchema.json` = JSON Schema);`toolChoice` 可 `auto` / `any` / `tool`
- 迴圈:`converse` → `stopReason == "tool_use"` 時取 `toolUse{toolUseId, name, input}` → 執行 → 以新的 `user` 訊息帶 `toolResult{toolUseId, content}` 回傳 → 直到 `end_turn`。**Bedrock 對 Converse 無狀態,對話歷史每回合重送**
- **結構化輸出**:`outputConfig.textFormat`(json_schema)或 `toolSpec` 加 `"strict": true`
- **串流**:`ConverseStream` 的 `messageStart → (contentBlockStart → contentBlockDelta* → contentBlockStop) → messageStop → metadata`;工具 input 以 partial JSON 分段串流
- **Prompt caching**:在 `system` / `tools` / `messages` 插 `cachePoint`

### 我們的實作處理了三個 Converse 實務陷阱

`agent/llm/bedrock.py`（目前 264 行）:

1. 空 text block 補空白
2. tool 結果合併成單一 `user.toolResult`
3. 相鄰同 role 合併(Bedrock 要求嚴格交替)

✅ **已完成的部分**:
- `BedrockProvider.chat_stream()` 已呼叫 `converse_stream`，依序產生 `delta` 與 `final`；主迴圈路會將文字增量轉成 `answer_delta`。
- 工具參數 partial JSON 重組、交錯文字/tool block、串流錯誤與主迴圈路分支均有自動化測試；Bedrock provider 專屬測試共 18 項。

⚠️ **仍存在的缺口**:
- **無 prompt caching** —— `grep cachePoint` 零命中。工具 schema 與多步 ReAct 仍會增加 token 成本與延遲。

### 模型選擇

`deploy/Dockerfile.agentcore` 已寫死 `ENV LLM_PROVIDER=bedrock`。AWS 上實際部署的 AgentCore Runtime 名稱為 `maia_agent`，runtime ID `maia_agent-4dRDgpAt4P`，2026-08-02 查詢狀態為 `READY`。ECS 部署腳本的線上 revision 2 基準 model 為 `us.anthropic.claude-opus-4-5-20251101-v1:0`。

⚠️ **程式碼與 `.env.example` 的 fallback 仍是 2024 年 model ID**，但正式 ECS 部署腳本已以 `BEDROCK_MODEL=us.anthropic.claude-opus-4-5-20251101-v1:0` 覆寫。新環境部署前仍應用 `aws bedrock list-inference-profiles` 確認該帳號與 region 可用的 inference profile。

⚠️ **per-token 價格建置時到 Bedrock 定價頁核對。**
