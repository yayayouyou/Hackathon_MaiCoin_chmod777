# MAIA 資料模型

> 專案自己產生的資料存在哪裡、該存在哪裡。
> 與 [`資料源地圖.md`](資料源地圖.md) 互補 —— 那份講「agent 去外面拿什麼」，這份講「我們自己留下什麼」。
> 來源：`agent-core/agent_ui/store.py`、`agent/audit_logger.py`、`agent/memory_store.py`、
> `agent/conversation_log.py`、`agent/trade_approval.py`、`skills/execution/live_guard.py`、
> `frontend-pixel/src/api/index.ts`。

## 一、現況盤點

專案的持久化狀態散在**八個地方**。只有兩個進了資料庫。

| 資料 | 現在存在哪 | 模組 | 有帳號維度 |
|---|---|---|---|
| 玩家帳號 · 世界進度 | ✅ **DynamoDB** | `agent_ui/store.py` | 有 |
| 登入 session | ✅ **DynamoDB** | `agent_ui/store.py` | 有 |
| 分析報告快照 | ✅ **S3**（私有 + presigned） | `agent_ui/app.py` | 無 |
| **討論串貼文** | ❌ **完全沒落地** | `api/index.ts`（mock） | 無 |
| **待核准訂單 token** | ❌ **行程內記憶體** | `agent/trade_approval.py` | 無 |
| 審計鏈（SHA256） | ⚠️ 本機 JSONL | `agent/audit_logger.py` | 無 |
| 下單決策台帳 · 24h 曝險 | ⚠️ 本機 JSONL | `skills/execution/live_guard.py` | 無 |
| agent 記憶（偏好 + 日誌） | ⚠️ 本機 JSON/JSONL | `agent/memory_store.py` | 無 |
| 完整對話存檔 | ⚠️ 本機 JSONL | `agent/conversation_log.py` | 只有 session_id |

⚠️ 的四項在容器重啟後消失。❌ 的兩項連重啟都不用等。

## 二、目標模型

**整個模型的主軸是 `username`。** 在有帳號之前，每個模組各自寫一份**全域**檔案 ——
十個人用就是十個人共用一份記憶、一條審計鏈、一份曝險額度。加上帳號維度之後，
這些資料才第一次有「這是誰的」這件事。

下圖中分區鍵不是 `username` 的三張表，都是刻意的例外。

## 三、三個真正的設計難點

搬到 DynamoDB 不只是換個地方寫。這三處**現有邏輯必須改**，照搬會壞。

### ① 雜湊鏈不能只是 append

鏈式雜湊要讀「上一筆的 `chain_hash`」才算得出這一筆
（`audit_logger.py:34-57` 的 `_load_last_chain_hash()`）。兩個併發請求讀到同一個前綴，
就會產生**兩條分岔的鏈** —— 而分岔的鏈驗不出「未被竄改」，等於這個賣點失效。

**做法**：`SK = seq` 單調整數，先用**強一致讀取**取回最後一筆，
再以 `attribute_not_exists(seq)` 條件寫入。撞號就重讀重試。

### ② 核准 TTL 的單調時鐘會被迫放棄

現在 `trade_approval.py:171` 刻意用 `time.monotonic()` 判斷 120 秒逾時，
註解寫明是為了「免受系統時間回撥／NTP 校正影響」。但 DynamoDB 的 TTL 只認 epoch **牆鐘**時間。

**折衷**：`expires_at` 用牆鐘供跨實例判斷與自動清理，同一實例內仍保留單調時鐘複查。
兩道都過才放行 —— 跨實例的正確性換來的代價，不該是把既有的防線拆掉。

### ③ 24h 曝險額度不能再靠掃檔案

`live_guard.py` 讀整份 `order_ledger.jsonl` 再過濾時間窗。資料量小的時候沒問題，
但那份檔案在容器重啟後會消失 —— **意思是重啟一次，20 萬 TWD 的額度就自動歸零重來**。
那不是資料遺失，是一道安全控制在無聲重置。

**做法**：改成 `SK between (now-24h, now)` 的區間查詢。不掃全表，額度也不會因重啟而失憶。

## 四、建置優先序

| | 表 | 不做會怎樣 | 估時 |
|---|---|---|---|
| **P0** | `maia_approvals` | App Runner 一旦擴到第二個實例，HITL 核准就 403 —— 台上最強的展示點會斷在按下確認的那一刻 | ~2h |
| **P0** | `maia_posts` | 發文重新整理就消失。部署一個「發文會不見」的網站，等於把這個洞公開展示 | ~4h |
| **P1** | `maia_orders` | 曝險額度因容器重啟而歸零。這比資料遺失嚴重 | ~3h |
| **P1** | `maia_audit` | 簡報宣稱「每個 AI 決策都可回溯且不可竄改」，但現在存在容器裡，重啟即失 | ~3h |
| **P2** | `maia_memory` · `maia_conversations` | 每個人有自己的偏好與對話史。加分不加命 | ~4h |
| **P2** | `maia_post_likes` | 按讚只是個可以無限點的計數器 | ~1h |

**P1 排在後面不是因為不重要**，是因為現場 demo 不會重啟容器，那兩個洞在台上不會現形。
但簡報如果寫「不可竄改審計鏈」，評審一問存在哪就會穿幫 ——
時間不夠時改講「審計鏈的雜湊機制」而不是「不可竄改的持久化」，這樣講是誠實的。

## 五、刻意不進資料庫的東西

| 資料 | 去哪 | 為什麼 |
|---|---|---|
| 艙位帳本 · FIFO 配對結果 | 本機快取 | 從 MAX API 推導的衍生資料，隨時可重建。存進資料庫只會多一份會過期的真相 |
| 分析報告快照 | **S3** | 大的 JSON 物件，且已在用 presigned URL 分享。DynamoDB 單項上限 400KB |
| MAX API 金鑰 | **Secrets Manager** | 鐵律：交易所金鑰不進瀏覽器，也不進應用資料庫 |
| 工具路由決策紀錄 | **CloudWatch** | 是可觀測性資料不是業務資料。查詢方式是聚合分析，不是主鍵取值 |

## 六、實體設定

| 項目 | 值 |
|---|---|
| 計費模式 | `PAY_PER_REQUEST` —— 不必預估容量，此規模實質零成本 |
| Region | `us-west-2`（與 `AWS_DEFAULT_REGION` 一致；Bedrock 用的是另一個 `BEDROCK_REGION`） |
| TTL 屬性 | `maia_sessions.expires_at`、`maia_approvals.expires_at` |
| 表名覆寫 | `MAIA_PLAYERS_TABLE`、`MAIA_SESSIONS_TABLE`（環境變數） |
| 本機開發 | `DYNAMODB_ENDPOINT_URL` 指向 DynamoDB Local；不設就走真正的 AWS |

⚠️ **DynamoDB 的 TTL 不是安全邊界。** 刪除是背景批次，官方說法「通常 48 小時內」——
過期的 session 還會被讀到很久。所以 `store.get_session()` 自己比對時間，
TTL 只負責省掉清理排程。這條有測試守著（`tests/test_auth.py`）。

```bash
docker run -d -p 8001:8000 --name maia-ddb amazon/dynamodb-local
DYNAMODB_ENDPOINT_URL=http://localhost:8001 AWS_DEFAULT_REGION=us-west-2 \
  python scripts/create_tables.py

# 正式 AWS
AWS_PROFILE=hackathon AWS_DEFAULT_REGION=us-west-2 python scripts/create_tables.py

# 驗證
python -m pytest tests/test_auth.py -q
```
