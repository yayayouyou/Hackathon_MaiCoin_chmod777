## 0. TL;DR — 七個定案

| # | 決策 | 一句話理由 |
|---|---|---|
| 1 | **Zone + Panel 兩張「顯式 barrel 註冊表」**，不做 Prop 註冊表 | barrel 保住編譯期型別安全（白畫面在現場 demo 是致命的，一行 merge conflict 不是）；Prop 註冊表要重構 1030 行換來 runtime crash，ROI 為負 |

| 5 | **一次性「接縫 PR」改完所有共用檔，之後凍結六個檔** | main.tsx 只有 7 行、index.html 17 行，五份提案有四份要改同一行；不先合併就是保證衝突 |

`_chunk` 把成品字串切碎後在**零延遲的 for 迴圈**裡 yield 完，一則 200 字回答會在同一個 microtask 丟出約 67 個事件、擠進同一兩個 TCP segment。而在第一個 Converse 回來之前，SSE body 是**零位元組**——沒有心跳、沒有 status。ReAct 上限 5 步（`orchestrator.py:19 _MAX_STEPS = 5`），走到 3 步就是 6–24 秒的死畫面。

**現況與仍需保留的韌性措施**

1. **真串流已完成**：`BedrockProvider.chat_stream()` 已處理 `ConverseStream` 的文字 delta 與 tool-use 分段輸入，並有自動化測試覆蓋。
2. **status／心跳仍有價值**：工具執行與模型首個事件前仍可能等待，UI 不應呈現無回應的死畫面。
3. **前端看門狗仍應保留**：首事件或事件間隔逾時時提供重試，不清除已收到的內容。paced reveal 只能作為顯示層保底，不再冒充後端串流。

### B3 · 反事實回測的頭條數字資本上不可行 → **算法本身有誤,結論已修正**

> **2026-07-30 狀態:本節的核心指控被推翻,但「不能當頭條」的建議仍然成立。**
>
> 本節拿 `hold_networth = 267,137,036`(續抱情境的**淨值**)當成需要的**本金**,那是錯的。
> 續抱只進不出、單調遞增,所以峰值本金 = 買進累計。而且原算法把「免費入金的幣」也算成本金 ——
> 主辦 CSV 的 223,487,907 之中有 **163,860,721(73%)是免費入金**,續抱情境跟實際情境一樣白拿,
> 根本不耗 TWD。
>
> **修正後的真實數字**:需要 **59,627,186** TWD 本金同時在場,是淨投入本金 24,274,547 的
> **2.46 倍** → `capital_feasible = True`。
>
> 實作在 `agent-core/skills/analytics/counterfactual.py`,已帶 `capital_feasible` /
> `hold_capital_required_twd` 與分級 caveat。**demo 講法從「續抱根本執行不了」改成
> 「續抱要 2.5 倍本金,而且整年一次都不能賣」** —— 仍然不適合當絕對金額的頭條,
> 但理由是「事後回看的反事實 + 需要 2.5 倍資金調度」,不是「資本上不可行」。
>
> 本節其餘建議(頭條換成擇時 alpha ≈ 0 與費率侵蝕、797 筆對帳異常做成第一張卡、
> 六軸分數改 logistic)**全部仍然成立且已實作**。以下原文保留供對照。

**實跑 `backend/analyze.py` 的真實輸出**
```
加密資產市值 : 1,638,514
已實現損益   : 253,449
twd_deposit  : 31,903,534      twd_withdrawal : 7,628,987
淨投入本金   : 24,274,547
─────────────────────────────
交易總額     : 211,543,739
估計手續費   : 338,470   (費率 0.16%, 資料未含)   ← 是假設值，不是實測
賣出vs續抱   : 26,598,877
買了就抱淨值 : 267,137,036     ← 需要 2.67 億本金
主動交易成本 : 26,937,347      ← 簡報頭條
餘額不一致列 : 797
```
`hold_networth = Σ(累積買進量 × last_price)`。這份 CSV 平均持有 2.7 天、同一批資本一年回收使用約 8.7 次，所以「買了就抱」需要 2.67 億本金同時在場，而帳戶只投入 2,427 萬。同一份報告裡「已實現損益 253,449」與「主動交易成本 26,937,347」差 100 倍。

MaiCoin 的量化或風控評審只要問一句「這個續抱情境需要多少本金？」，整份報告的可信度當場歸零——**不只丟創意 25%，後面每個數字都會被打問號**。

**修法（P0，3h）**
1. `backtest.py` 加 `capital_feasible: bool`（`hold_networth > 3 × 淨投入本金` 就是 False）與 `hold_capital_required_twd`。UI 在 False 時**自動把絕對金額降級為註腳**並顯示「此情境需要 NT$2.67 億同時在場，超出本帳戶淨投入 2,427 萬，僅供方法學示意」。
2. **頭條換成兩個經得起追問的數字**：
   - **擇時 alpha ≈ 0**：買單 77% 落在均價之上、賣單也 77%，`timing_skill = -0.8%` → 「你的進出場時機與隨機無異」。這個結論不依賴資本假設，方法學乾淨。
   - **手續費侵蝕 / 淨投入本金** = 338,470 / 24,274,547 ≈ **1.39%/年**，並在 UI 上讓費率成為**可調下拉**（maker / taker / VIP 分級），旁邊掛「假設」標記。
3. **把「797 筆餘額不一致」做成畫面上第一張卡**：「MAIA 讀進 10,000 筆紀錄，第一步是對帳，發現 797 筆餘額不一致並主動揭露」。對一家做合規／信託／ISO 27001 的公司，主動對帳比任何漂亮數字都更像「這能變成我們的產品」。
4. 六維分數修正：實跑值是 `活躍度 100.0 / 紀律 0.0 / 擇時 45.9 / 分散 79.2 / 持有耐心 5.4 / 風險控管 55.4`——兩個軸貼死在 0 和 100。把線性 clamp 換成 logistic，讓極端值落在 5–95（2 行），雷達才看起來像儀表而不是壞掉的量表。

## 4. (a) 擴充架構的便利度 —— Zone 契約與註冊機制

### 4.1 現況成本 vs 目標成本

| | 今天 | 接縫 PR 後 |
|---|---|---|
| 新增一個彈窗面板 | 3 檔 4 處（`types.ts` union、新檔、App.tsx import、App.tsx 條件鏈） | **2 處**：新檔 + `panels/index.ts` 一行 |

| 新增一個 HUD 區塊 | 沒有基礎設施 | **2 處**：`hud/blocks/` 新檔 + `channels.ts` 一行 |
| 新增一個功能入口 | 沒有 | **1 處**：`features/registry.ts` 一筆 |

**全隊共用的 append 點總共只有四行**：`panels/index.ts`、`zones/index.ts`、`hud/channels.ts`、`features/registry.ts`。四個都是一行 append，5 秒可解，而且 git 會如實報告衝突——這正是我要的（比 runtime 靜默錯誤好一個數量級）。

### 4.2 為什麼是「顯式 barrel」不是「glob 自動掃描」

glob 的賣點是「零共用檔編輯」，但它把三類錯誤從編譯期搬到執行期：

- 兩個人都把面板叫 `'report'` → git 零衝突、typecheck 過（不同檔的字串字面值不衝突）、vite dev **不做 typecheck**（`typecheck` 是分開的 script）→ 合併後開頁面白畫面，錯誤指向 `engine/panels.ts` 而不是任何人的檔案。
- `travel` 目標打錯字 → 執行期才發現。
- 正式 build 不跑 `validateWiring()`。

barrel + `as const satisfies` + `keyof typeof` 把這三類全部變成**紅色編譯錯誤**，代價是一行 append。在 30 小時、只有一台 demo 機、最後 4 小時沒有時間 debug 的情境下，這個交換是壓倒性的。

```ts
import type { Accent, Room } from '../world/types';

/** zone 之間傳遞的參數。討論室的 roomId、DNA 室的幣種都走這裡。 */
export type ZoneParams = Record<string, string | number | boolean>;

export type ZoneCtx = {
  id: string;
  params: ZoneParams;
  /** 從哪個 zone 走過來。開場是 null */
  from: string | null;
};

export type ZoneRuntime = {
  room: Room;
  /**
   * 非同步回來時玩家可能已經換場了。所有 .then() 都要包這個。
   * 這取代了 game/index.ts:107-114 那段硬編的 `if (room.id === 'discussion')`。
   */
  ifStillHere: (fn: () => void) => void;
  /** 換場時自動 abort。輪詢與 fetch 都要吃它，否則離開房間還在打 API */
  signal: AbortSignal;
  /** 餵 NPC 對話泡泡。空陣列 = 這個房間沒人講話 */
  setChatter: (lines: string[]) => void;
};

/**
 * 這個區塊在中庭的門面。宣告了就自動長出一道門，
 * 完全不必去改 atrium.ts —— 這消滅了「門座標在 props 與 portals
 * 各寫一次、型別守不到、抄錯的症狀是看得到門但走過去沒反應」這個地雷。
 */
export type ZoneGateway = {
  /** 門牌上的名字。2–6 個字 —— 名牌寬度上限 128px */
  label: string;
  enterLabel?: string;
  accent: Accent;
  /**
   * 只有既有兩道門會用（它們的座標被 12 項測試鎖死）。
   * 新 zone 一律不填，由 atrium 依 zone id 字母序自動配位 ——
   * 讓人自己選 slot 編號會產生「兩個 zone 搶同一格 → 兩道門重疊
   * → 其中一道永遠打不開 → git 零衝突、TS 零錯誤」的靜默失敗。
   */
  pinned?: { x: number; y: number };
  /** 省略 = travel 到這個 zone。也可以先開一個選擇面板（討論區就是這樣） */
  action?: { type: 'panel'; panel: PanelId };
};

export type ZoneDef = {
  id: string;
  title: string;
  accent: Accent;
  /**
   * 建房間。每次進場呼叫一次，可以依 params 參數化 ——
   * 12 間討論室共用一個 zone 就是靠這個。
   * ⚠ build 內才可以呼叫 listZones()，module 層呼叫會拿到不完整的表。
   */
  build: (ctx: ZoneCtx) => Room;
  /** 進場副作用：載資料、餵 NPC 台詞、開輪詢。回傳 cleanup。 */
  onEnter?: (ctx: ZoneCtx, rt: ZoneRuntime) => void | (() => void);
  gateway?: ZoneGateway;
};

/** 純粹是型別輔助，讓 zone 檔案在自己內部就享有完整檢查。 */
export const defineZone = <T extends ZoneDef>(z: T): T => z;
```

#### `src/world/zones/atrium.ts` —— gateway 自動配位（座標契約）

```ts
/**
 * 中庭門位。
 *
 * pinned 的兩道門座標被 12 項測試寫死（portals.mjs:13,31,44、rooms.mjs:7、
 * interaction.mjs:62、layout.mjs:64,68 都用世界絕對座標導航），永遠不能動。
 * 上排四格是新區塊的空位：實測上牆設施全在 y ≤ 96、柱子在 x 96–112 與
 * 848–864，四個門位（32×52，propSolid 回 null 不擋路）全部淨空；
 * 與排行看板 (452–508, y186–234) 無 x 重疊。
 *
 * ⚠ 相鄰門的 x 距離必須 ≥ 128（名牌寬度上限）。目前是 128/288/128。
 */
const OPEN_SLOTS = [
  { x: 208, y: 150 },
  { x: 336, y: 150 },
  { x: 624, y: 150 },
  { x: 752, y: 150 },
] as const;

function gateways(): Door[] {
  const all = listZones().filter((z) => z.gateway && z.id !== 'atrium');
  const pinned = all.filter((z) => z.gateway!.pinned);
  const auto = all
    .filter((z) => !z.gateway!.pinned)
    .sort((a, b) => a.id.localeCompare(b.id));   // 決定性配位，測試算得出來

  return [
    ...pinned.map((z) => door(z, z.gateway!.pinned!.x, z.gateway!.pinned!.y, {
      label: z.gateway!.label, enterLabel: z.gateway!.enterLabel,
    })),
    ...auto.slice(0, OPEN_SLOTS.length).map((z, i) => door(z, OPEN_SLOTS[i]!.x, OPEN_SLOTS[i]!.y, {
      label: z.gateway!.label, enterLabel: z.gateway!.enterLabel,
    })),
  ];
}
```

## 6. (c) 場景分散 —— 選「重新配置區塊」，不選「縮小總覽」

### 6.1 決策與理由

使用者給的兩個方向：(i) 一開始畫面縮小看整個空間、移動時放大；(ii) 重新調配區塊設計。

**選 (ii)，並用 Deck 快捷格補足 (i) 想達到的「一眼知道有什麼」。**

否決 (i) 的四個硬理由（全部實測）：

1. **只能整數跳階**。`core.ts:51` 是 `s = max(1, round(min(innerW/480, innerH/270)))`，`view = min(1024, ceil(視窗/s))`。1920×1080 的 natural=4，降一階 s=3 得 640×360——**看不到 960×512 的中庭**。要看到就得 s=2（降兩階）。
2. **1280×720 是最常見的投影機協商結果，兩種倍率下都是 640×360**，比提案宣稱的「保證可視框 640×384」矮 24px。同一個「地圖模式」在不同機器上面積差 2.25 倍。
3. **`#world-labels` 是 `overflow:hidden`**（`styles.css:58`）。上排門的名牌掛在世界 y=148，1366×768 拉遠時 `cam.y ≈ 142`，名牌上半被裁掉——「拉遠＝儀表板」的賣點變成半截字的 bug。
4. **CSS transform 補間是非整數縮放**，直接違反 `core.ts:38-43` 與 `tests/screen.mjs:16` 雙重保證的「整數倍不可妥協」，中文 DOM 字會在那 220ms 糊掉。加上 iris 0.26+0.26，每次換房是 1.6 秒、其中 1.1 秒凍結輸入。

### 6.2 (ii) 的具體做法：中庭放射，**只加不移**

「分散」的真正病因不是缺總覽，是**星狀拓樸 + 出生點只看得到 25% 的空間**：大廳 960×512，出生 (480,322)，走動視野約 427×256。

### 6.3 進場取景（保留，但降到最小且條件式）—— P2，1.5h

`loadRoom()` 時 iris 收到 r=0 的那一瞬間畫面是全黑的（`render.ts:399-403` 塗滿 `C['0']`），**此時換 backbuffer 尺寸沒有人看得到**。所以：

```ts
/**
 * 求「能讓整個房間入鏡的最大整數倍率」。求不到（房間比視野大）就回 null，
 * 表示這台機器不做進場取景 —— 這比在 720p 上顯示 2/3 個中庭好。
 */
export function framingScale(room: { w: number; h: number }): number | null {
  const natural = Math.max(1, Math.round(Math.min(innerWidth / 480, innerHeight / 270)));
  const floor = Math.max(1, Math.ceil(Math.max(innerWidth, innerHeight) / 1024)); // MAX_VIEW 夾制
  for (let s = natural; s >= floor; s--) {
    if (Math.ceil(innerWidth / s) >= room.w && Math.ceil(innerHeight / s) >= room.h) return s;
  }
  return null;
}
```

流程：`iris 全黑 → framingScale() 有值就套用 → 停 0.45s → iris 張開 → 立刻回 natural（同樣在一幀內完成，沒有補間）`。任何 WASD / pointerdown 立刻取消停留。

**沒有 CSS transform 補間、沒有 Tab 切換地圖模式、沒有雙標籤層。** 這三樣是提案一 23h 的大宗，也是全部風險的來源。

> 640×384 的由來：`min(view.w) = 640`（1280×800 的 s=2）、`min(view.h) = 384`（1366×768 的 s=2）。這是「在多數桌機上取景成功」的最大安全尺寸。中庭 960×512 只有在 1920×1080 上取景成功——這是可接受的漸進增強。

### 7.3 HUD 資料通道（React 骨架 + LiveText）

```ts
// src/hud/live.ts —— 零相依
export type Live<T> = { get(): T; set(v: T): void; sub(fn: (v: T) => void): () => void };

export function live<T>(init: T): Live<T> {
  let v = init;
  const subs = new Set<(v: T) => void>();
  return {
    get: () => v,
    set(next) { if (Object.is(next, v)) return; v = next; for (const f of subs) f(v); },
    sub(fn) { subs.add(fn); return () => void subs.delete(fn); },
  };
}
```

```tsx
// src/hud/LiveText.tsx
/**
 * 把一個 live 通道綁到一個 <span> 的 textContent。全程不呼叫 setState。
 *
 * 這是 worldLabels.ts 那套「每個 setter 自己手寫 diff」的紀律，
 * 收斂成一個共用元件裡的三行。
 *
 * ⚠ fmt / dir 必須是模組級的穩定函式（不要寫 inline 箭頭），
 *   否則 effect 每次 render 都會退訂重訂。
 */
export function LiveText<T>({ ch, fmt, dir, className }: {
  ch: Live<T>; fmt: (v: T) => string; dir?: (v: T) => string; className?: string;
}) {
  const ref = useRef<HTMLSpanElement>(null);
  useEffect(() => {
    const el = ref.current; if (!el) return;
    const write = (v: T) => {
      const s = fmt(v);
      if (el.textContent !== s) el.textContent = s;      // diff
      if (dir) { const d = dir(v); if (el.dataset.dir !== d) el.dataset.dir = d; }
    };
    write(ch.get());
    return ch.sub(write);
  }, [ch, fmt, dir]);
  return <span ref={ref} className={className} />;
}
```

## 8. (e) 模組切分給隊友

### 8.1 最重要的一個發現：美術是不可平行化的技能瓶頸

實測：`frontend-pixel` 的**每一行**像素美術（三場景、23 支道具、9 份角色圖、10 份地磚、132 項測試）都出自單一作者。`props.ts` 有約 120 次 `fillRect/ellipse/gradient`，單支道具 10–64 行純手排整數偏移，零圖檔、零預覽工具、零參考圖流程；迭代迴圈是「改數字 → HMR → 操控角色走過去 → 瞇眼看」，一輪 30–60 秒。

**把三個新 zone 的美術切給三個隊友，換到的不是產出，是返工**：受光方向畫反（`bevelBox` 亮邊固定左上）、用了不在 36 色調色盤裡的顏色（`tests/art.mjs` 只掃 `sprites.ts` 與 `tiles.ts`，掃不到 `props.ts`）、忘了寫 `propLights` 導致道具在壓暗房間裡是個黑洞。三個房間並排會像三個不同專案。

**做法：用「組合」取代「繪製」。**

- 美術負責人**獨佔** `art/`、`game/props.ts`、`props/kit.ts`、`game/render.ts`。
- 他的第一件事是產出 **6–8 支參數化槽位道具**（`props/kit.ts`），每支吃 `accent` 與一塊留白給 DOM 中文標籤：
  `screenPanel(x,y,w,accent)` / `pedestal` / `kiosk` / `archSign` / `dataPillar` / `floorRune` / `deskUnit` / `podium`。
  這些**全部用既有 23 種 Prop 變體組出來**（screenwall / terminal / chartboard / board / counter / trustdesk…），不新增 Prop kind → 不動 `types.ts` → 零共用檔衝突。
- 隊友的 zone 只准用 kit 組合。真的需要新道具 → 開 issue 給美術負責人。

凍結清單：`src/main.tsx`、`index.html`、`src/ui/App.tsx`、`src/ui/uiStore.ts`、`src/game/index.ts`、`src/world/types.ts`。
要動 → 開 issue 給 integrator 批次處理。

**規則 2 · 全隊只有四個 append 點，都是一行。**
`world/zones/index.ts`、`ui/panels/index.ts`、`hud/channels.ts`、`features/registry.ts`。
git 會如實報告衝突，5 秒可解——這遠比「零衝突但白畫面」好。

**規則 3 · CSS 用 `@layer` 徹底消滅順序依賴。**
`styles.css` 頂端宣告 `@layer core, zone, hud, pro;`，各層各自包起來。這讓「hud.css 必須在 styles.css 之後 import 才能覆寫 `.scene-title`」這種脆弱設計直接消失。
另外**在接縫 PR 就預先開好變體插槽**，讓沒有人需要改 core：
`.btn[data-variant='danger'|'ghost']`、`.field[data-size='sm']`、`.panel-body[data-flush]`、`.panel[data-size='xl']`。
zone 的 CSS 一律 `.z-<id>-` 前綴，並由 `tests/art.mjs` 的正則守（規則沒有機器守 = 沒有規則）。

**規則 4 · 全域命名空間表（唯一真實來源，就是這張表）。**

| 命名空間 | 誰擁有 | 撞了會怎樣 | 守門 |
|---|---|---|---|
| zone id | `zones/index.ts` barrel | 編譯錯誤 ✓ | TS |
| panel id | `panels/index.ts` barrel | 編譯錯誤 ✓ | TS |
| prop kind | 美術負責人獨佔 | 編譯錯誤 ✓ | TS |
| CSS class | `.z-<zoneid>-` 前綴 | 樣式互相污染 | `tests/art.mjs` 正則 |
| HUD 通道 | `channels.ts` | 編譯錯誤 ✓ | TS |
| gateway 門位 | atrium 自動配位 | 不可能撞（沒人選） | `tests/zones.mjs` 驗兩兩不重疊 |
| api 端點 | `api/index.ts` + `maia.*` | 執行期 404 | `tests/api.mjs` |

**規則 5 · 測試擁有權下放。**
`tests/run.mjs` 的 SUITES 改成掃描 `tests/*.mjs`（10 行改動），之後新增套件是純新檔、零共用編輯。
座標型斷言下放到各 zone 自己的 `zone.test.mjs`——誰擁有座標誰擁有斷言。
integrator 只保留三個**不變式套件**：`art`(7) + `screen`(24) + `movement`(10) = 41 項、實測約 50 秒，這三個不依賴任何座標。

**規則 6 · 兩個 gate。**
- **merge gate（約 60 秒）**：`tsc -p tsconfig.gate.json --noEmit` + `node tests/run.mjs 像素圖 畫布尺寸 移動與鏡頭` + 新的 `tests/zones.mjs`。
  （`tsconfig.gate.json` extends 主檔但把 `noUnusedLocals` / `noUnusedParameters` 設 false——實測這兩項是開的，半成品 zone 一定有暫時沒用到的 import，逼人寫 `void x;` 或註解掉 import 然後忘記解開。正式 `npm run build` 仍用嚴格版。)
- **full gate（實測 156 秒，序列執行）**：integrator 每隔一段時間跑一次；最後階段改成每次合併都跑。

### 8.4 兩個必須先修的測試基建陷阱

**陷阱 A · `ensureServer()` 會靜默測試「當下 :5173 上跑著的那份程式碼」。**
`harness.mjs` 先 ping BASE，通了就直接沿用，不驗證那台 server 服務的是哪個分支。integrator 開著自己分支的 `npm run dev`、checkout 隊友分支跑測試 → 132 項全綠但測的是自己的程式碼。
**修**：`ensureServer` 未指定 `BASE_URL` 時一律用隨機 port 並強制自己起 server。

**陷阱 B · `collectedErrors.length === 0` 會被真 fetch 打爆。**
`harness.mjs:53-55` 收集所有 `console type==='error'`，而 `screen.mjs:44`、`portals.mjs:107`、`interaction.mjs:80`、`rooms.mjs:42`、`touch.mjs:47` 都斷言它為 0（screen 是 6 種尺寸各一次，共 10 個斷言）。瀏覽器對失敗的 fetch 會自己吐 error-level console 訊息，`console.warn` 換不掉。
**修**：白名單忽略 `Failed to load resource` 與 `net::ERR_` 開頭（3 行）；且 `?fast=1` 不打真後端。

### 8.5 `?gallery=1` 道具展示場 —— 30 分鐘，全案最高 ROI 的基礎建設

一個把所有已註冊道具畫在網格上、標 kind 名稱與尺寸、附打光開關與格線疊層的除錯場景。五份提案沒有一份提到它，但**沒有它就談不上讓第二個人碰美術**。同時它也是隊友挑 kit 道具的目錄。

## 附錄 B · 零相依規範（不可違反）

1. **零外部 CDN、零 CSS 框架、零新 runtime 相依。** 實測 `package.json` 的 dependencies 只有 `react` + `react-dom`。字體用 system stack（`styles.css:18`）。這是離線 live demo 的前提。**不要引入 react-query / zustand** —— `useAsync` 的輪詢語意（重抓不翻 loading、不清資料、錯誤保留舊值）已經為這個 UI 調過，換掉會讓行情列表每 3 秒閃爍。
2. **整數倍縮放不可妥協。** `core.ts:38-43` + `tests/screen.mjs:39-43` 雙重保證。任何 zoom 只能在整數級距間跳，沒有 2.5x。
3. **中文一律走 DOM，不畫進 480×270 的 backbuffer。** canvas 內只能畫 `shapes.ts:138` 那 18 個 5×7 拉丁點陣字元。
4. **每幀變動的東西不進 React。** `#ui-root` 走動 2 秒 DOM 變動必須 = 0；`#hud-root` 的 childList + attributes 也必須 = 0（數值走 `textContent`）。
